## Layout and Accessibility

A compact dark-purple grid intro is followed by an unframed two-column layout: direct contact on the left, form on the right. Mobile stacks those areas in reading order. Shared typography, Container, Button, spacing, colors, grid treatment, and Header/Footer are reused without primitive changes.

The page has one H1 and logical H2 headings. Direct-contact methods are semantic links within an address/list, with localized labels and decorative icons hidden from assistive technology. The form has an accessible name, explicit labels, native required attributes, email/tel input types, autocomplete, 16px input text, minimum 48px controls, and a vertically resizable message field.

Field errors are textual, linked with `aria-describedby`, and exposed through `aria-invalid`, not color alone. After a response, focus moves to the first invalid field or the form status. A polite atomic status announces pending and result text; controls are disabled while the action is pending. Controlled input values remain available after validation and unavailable-delivery responses. No-JavaScript responses also preserve submitted values through server-rendered action state. The existing skip link, navigation focus styles, and reduced-motion rules remain unchanged.

## Form Architecture

- `ContactPage` is a Server Component. Only `ContactForm` adds a client boundary for action state, retained input, pending UI, and focus management.
- A native Server Action in `app/[locale]/[page]/actions.ts` validates the bound locale and submitted FormData. Previous client form state is never treated as validation or delivery evidence.
- `lib/contact.ts` defines shared field names, limits, error codes, and state types. `lib/contact-validation.ts` is the small explicit validator used by the action and focused tests. No form/schema library was installed.
- `useActionState` uses the localized Contact permalink for progressive enhancement. The form uses `noValidate` so error messages are consistently localized by the server rather than browser-language-dependent validation bubbles; required/type/maxlength semantics remain present.
- `lib/contact-delivery.ts` is the server-only delivery boundary. Its current adapter reports unavailable and performs no network request, persistence, queue operation, or application logging of submitted data.

The implementation follows the native patterns described by the [Next.js forms guide](https://nextjs.org/docs/app/guides/forms) and [React useActionState reference](https://react.dev/reference/react/useActionState).

### Validation Rules

| Field | Rule |
| --- | --- |
| Name | Required non-whitespace text; maximum 120 characters |
| Email | Required; basic email syntax; maximum 254 characters |
| Phone | Optional; common international numeric formatting accepted; at least five digits when supplied; maximum 32 characters |
| Message | Required non-whitespace text; multiline allowed; maximum 5,000 characters |

Values are trimmed. Duplicate field entries, files in text fields, disallowed control characters, embedded line breaks in single-line fields, and over-limit input are rejected. Reflected error values are bounded to the field limit, so oversized forged input is not echoed without bounds. Unknown extra fields are ignored and never forwarded to delivery. Browser attributes are convenience constraints, not the security boundary.

Native Server Action protections are retained; none were loosened. No CAPTCHA, honeypot, third-party tracking, or inaccessible spam control was added. Validation is not a complete anti-spam strategy: deployment-appropriate rate limiting and operational abuse controls remain required before delivery is enabled.

## Delivery Status and Required Integration

No email/SMTP dependency, integration code, provider configuration, or environment file was found in the repository. The page therefore displays an upfront delivery-unavailable notice. A valid submission returns an explicit not-sent response. Validation alone never triggers a success state. No message is delivered, queued, or stored by the application.

The typed state includes provider failure and acceptance messages for the future adapter. Success is only selected for an `accepted` provider result, which the current adapter cannot return. Unexpected provider exceptions map to a generic localized failure response without exposing implementation details. Actual provider success, provider failures, and transport-failure recovery cannot be verified end to end until an integration exists.

Before enabling delivery:

1. Choose and authorize an email provider or SMTP service.
2. Configure server-only credentials, verify the sending domain/address, and confirm the recipient. The public email address is not proof of the legacy form's recipient setting.
3. Implement `contactDelivery.send` with safe message construction, validated reply-to handling, timeouts, and real provider acknowledgement. Do not return `accepted` merely because input validated.
4. Add deployment-appropriate rate limiting/spam protection and decide retry/idempotency and operational monitoring behavior without logging message bodies unnecessarily.
5. Test real acceptance/failure behavior and delivery to the agreed recipient; review applicable privacy/retention copy before accepting live inquiries.
6. Set availability only when that integration is genuinely ready. Keep unavailable behavior otherwise.

No provider, credentials, recipient configuration, or WordPress plugin internals were invented.
